# CLAUDE.md — Shai-Hulud Guard

This file is the instruction surface for Claude Code when working on this repository. It is the **single source of truth** about how the codebase is laid out, which invariants must never be regressed, where IOC data comes from, and what is still missing from the project infrastructure.

> **Read this file fully before editing any `.py` file.** This is a security tool. A subtle mistake — adding a `requests` import, broadening a regex, executing tarball code, auto-revoking a token — can either render the scanner blind, produce false negatives that mislead a victim during active incident response, or cause irreversible data loss on a developer machine.

## 2. The two versions, side by side

### v1.1.0 — `shai_hulud_guard.py`

Flag-based, non-interactive. Three top-level modes wired in `main()`.

**CLI surface** (do not break this — it is the contract for CI usage and downstream scripts):

```
python shai_hulud_guard.py --scan [--path DIR]
python shai_hulud_guard.py --check <pkg>[@<version>]
python shai_hulud_guard.py --incident
python shai_hulud_guard.py --version
```

**Top-level functions** (`shai_hulud_guard.py`):

| Function | Purpose |
|---|---|
| `run_scan(project_path)` | Six sequential checks. Prints inline via `ok`/`warn`/`crit`/`info`/`subh`. Returns total finding count. No structured `Finding` object — output is plain text. |
| `run_check(spec)` | Five-step pre-install analysis: registry metadata → known-bad DB → lifecycle scripts → dependency sources → tarball download + SHA-512 verify + deep scan. Accumulates `risk_score` capped at 100. **Never executes the package.** |
| `run_incident(brief=False)` | Static 8-step playbook printed to stdout. Auto-invoked at the end of `run_scan` when the persistence daemon is detected (`brief=True`). |

No verbosity flag (`-v`/`-q`). No JSON output. No exit code mapped to severity. These are deliberate v1.1 limits — propose changes before adding.

### v2.0.0 — `shai_hulud_guard V2.0.py`

Interactive menu-driven. Adds a structured `Finding` dataclass, an auto-fixer with per-finding confirm prompts, a "proactive protections" stage with disclosed tradeoffs, and an LLM-ready diagnosis report writer.

**CLI surface**:

```
python "shai_hulud_guard V2.0.py"                 # interactive (recommended)
python "shai_hulud_guard V2.0.py" --path DIR      # interactive, scan specific project
python "shai_hulud_guard V2.0.py" --check PKG     # non-interactive pre-install check
python "shai_hulud_guard V2.0.py" --version
```

**Top-level functions** (`shai_hulud_guard V2.0.py`):

| Function | Purpose |
|---|---|
| `collect_system_info()` | Runs `node --version`, `npm --version`, `git --version` via `subprocess` with 5s timeout. Returns dict including `os`, `python`, `cpu`, `hostname`, `user`, `ci_env`, `shell`, `scanned_at` (UTC). **No credential values are collected.** |
| `Finding` (dataclass) | `check`, `level` (CRITICAL/HIGH/MEDIUM/LOW/INFO), `title`, `detail`, `path`, `fixable`, `fix_label`, `fix_fn` (Optional Callable). `fix_fn` is excluded from `repr` so dataclass dumps don't capture closure state. |
| `run_scan(project_path)` | Six checks, returns `List[Finding]`. Each check uses `tick()` spinner + `done_line()`. Findings carry their own fix closure when auto-fixable. |
| `run_autofixes(findings)` | Iterates fixable findings. **Each fix individually confirmed.** Followed by a printed list of manual steps that require authentication (token revocation, IAM key disable, etc.). |
| `run_protections(project_path)` | Iterates `Protection` objects from `build_protections()`. **Each protection prints BENEFIT + TRADEOFFS before asking to apply.** Some have a `verify_fn` that re-reads `npm config get` to confirm state. |
| `generate_diagnosis_report(...)` | Writes `shai_hulud_report_<UTC-timestamp>.txt` containing system info, findings, deps, credential file presence (names only), fixes applied, protections applied, and 7 prompt questions for the LLM. **No file contents and no credential values are included.** |
| `run_package_check(package_spec)` | Same five-step analysis as v1.1's `run_check` but returns `(risk_score, List[Finding])` for integration with the interactive flow. |
| `show_incident_guide()` | Eight-step playbook, identical content to v1.1's `run_incident` but rendered with the v2.0 UI helpers. |
| `main()` | Argparse → interactive loop → main menu → post-scan menu (`D`/`F`/`P`/`R`/`C`/`I`/`M`). |

**v2.0 introduces four `Protection` objects** (`build_protections`):

1. `age_check_script` — writes `npm_safe_install.py` to the project root. A standalone age-gate wrapper that checks publish date via the registry before calling `npm install`. Default `MIN_AGE_DAYS = 7`. **npm 10 has no native `min-release-age` config** — this is the workaround. The file is generated at runtime; do not check it into git.
2. `save_exact` — `npm config set save-exact=true` globally. Has a `verify_fn` that re-reads via `npm config get save-exact`.
3. `project_ignore_scripts` — appends `ignore-scripts=true` to project `.npmrc`. Does **not** block git/file transitive deps — `prepare` hooks still run on those. This caveat must remain in the tradeoff disclosure.
4. `gha_pin_report` — scans `.github/workflows/*.yml` for `uses: …@vX` tag pins, writes `shai_hulud_pin_actions.txt` listing them. **Report-only, no automated YAML edits.**

## 3. Shared code architecture (applies to both versions)

The two scripts share the same constants, the same pattern engine, and the same scanning logic. Where line numbers are quoted below they refer to v2.0; v1.1 line numbers are close but not identical.

### Pattern engine — `scan_text(text)`

Runs every `(regex, description, risk)` tuple from `MALICIOUS_PATTERNS` against arbitrary text using `re.search(..., re.IGNORECASE)`. Dedups results by `(description, risk)`. Returns `List[(desc, risk, snippet[:100])]`.

Called from:
- `run_scan` — against each lifecycle script value in installed `node_modules/*/package.json`
- `run_package_check` — against each declared lifecycle script in registry metadata
- `scan_tarball_bytes` — against every text-like file inside the downloaded tarball

### Tarball scanner — `scan_tarball_bytes(data: bytes)`

Reads the gzipped tarball **in memory** via `tarfile.open(fileobj=io.BytesIO(data), mode="r:gz")`. Walks `getmembers()`, checks each file's basename against `MALICIOUS_FILENAMES`, and for members whose suffix is in `TEXT_EXT` (`.js .mjs .cjs .ts .tsx .json .sh .bash .py .yml .yaml .env`) calls `extractfile(m).read().decode("utf-8", errors="replace")` and pipes the content into `scan_text`.

**Nothing is ever extracted to disk. Nothing is ever executed.** Preserve this if you refactor — see invariants in §5.

### Network — `_fetch_json` / `_fetch_bytes` (v2.0) / `fetch_json` / `fetch_bytes` (v1.1)

Both wrap `urllib.request.urlopen` with a `User-Agent` header (`shai-hulud-guard/<VERSION>`). 12s timeout for JSON, 45s for tarball bytes. **Adding a `requests` import breaks the "zero external dependencies" promise that is stated in the script docstring, the README, and the help banner.** It is also a documented hardening choice (`requests` would expand the supply chain surface of a security tool).

### Risk scoring (in `run_package_check` / `run_check`)

Score weights are inline, not centralised. The thresholds below drive the verdict copy in the printed summary — touch deliberately, and update the verdict tiers in lockstep.

| Indicator | Score delta |
|---|---|
| Published `<6h` ago | +40 |
| Published `<24h` ago | +25 |
| Published `<7d` ago | +10 |
| `KNOWN_BAD` package, version not in `bad` list | +15 |
| Lifecycle script matches `CRITICAL` pattern | +45 |
| Lifecycle script matches `HIGH` pattern | +20 |
| Lifecycle script matches `MEDIUM` pattern | +5 |
| `preinstall` hook present (any content) | +5 |
| Git/file/http(s) transitive dep | +12 each, capped at +30 |
| Tarball >800 KB | +10 |
| Tarball pattern match `CRITICAL` | +50 |
| Tarball pattern match `HIGH` | +20 |
| Tarball pattern match `MEDIUM` | +5 |
| **SHA-512 (or SHA-1) integrity mismatch** | **+100** (immediate verdict) |

Verdict tiers:
- `0` → Proceed with caution
- `1–14` → Low — manual review recommended
- `15–39` → Moderate — verify independently
- `40–69` → High — investigate before installing
- `≥70` → **CRITICAL — do not install**

If you add a new weight, document it here. The user-facing report copy and the LLM diagnosis prompt depend on these tiers being meaningful.

## 4. Signature database — where IOC updates land

These five module-level constants are the **only place** new IOCs should be added. Both scripts maintain them in parallel — keep the two in sync, **the v2.0 file is currently the canonical / more conservatively-trimmed version** but v1.1 has slightly broader regexes (it includes `signal.org`, `bunx\b`, `.npmrc` access at MEDIUM, an `actions/cache.*restore-keys` LOW tier, and the `Sha[i1].?Hulud|Shai.?Hulud` alternative). When adding a new IOC, decide whether it belongs in both, then update both.

### 4.1 `MALICIOUS_FILENAMES`

Exact basenames of files dropped by the worm. Flagged regardless of content. Keep this set small and high-confidence — every entry is a hard block.

```python
{ "router_init.js", "setup_bun.js", "bun_environment.js", "setup.mjs" }
```

### 4.2 `MALICIOUS_PATTERNS`

List of `(regex, description, risk_level)` tuples. `risk_level` **must** be one of the literal strings `"CRITICAL" | "HIGH" | "MEDIUM" | "LOW"` — `scan_text`, the risk scoring branches, and the colour-mapping in `Finding._col()` all `==`-compare against these exact strings. A typo silently demotes a finding.

When adding patterns, follow these rules:
- Use a non-greedy match where possible.
- Test the regex against a known clean repo (lodash, ts-node, react, vue) before merging — false-positives in an installed `node_modules` tree will drown out real findings.
- Cite a public source in the surrounding comment (see §5.5).

### 4.3 `KNOWN_BAD`

Dict `{ package_name: {"bad": [versions], "waves": [wave_tags]} }`.

Two semantics:
- `bad: ["1.169.5"]` → install of this exact version triggers a `CRITICAL` finding and stops `run_package_check` at risk = 100.
- `bad: []` (empty) → the package is on the high-scrutiny watchlist. No version is confirmed malicious yet, but it has been targeted before — `run_package_check` adds +15 risk and emits a MEDIUM finding.

`waves` is a free-form list of human tags (e.g. `"Wave5-May2026"`) used in the report copy. Keep these consistent with the README's attack-timeline table.

### 4.4 `HIGH_VALUE_TARGETS`

`set(KNOWN_BAD.keys()) | {extra packages repeatedly attacked}`. Used by `run_scan` to upgrade a finding to `HIGH` even when the installed version is not on the `bad` list, and by the diagnosis report to flag deps in the package listing.

### 4.5 `DAEMON_PATHS`

Per-OS absolute paths where the worm's persistence daemon installs itself.

```python
{
  "linux":   [~/.config/systemd/user/gh-token-monitor.service],
  "darwin":  [~/Library/LaunchAgents/com.user.gh-token-monitor.plist],
  "windows": [],  # not publicly documented at v1.1 / v2.0
}
```

The Windows list is **intentionally empty** — public post-mortems have not documented a confirmed Windows persistence path. Do not fill it in with guesses. If a Windows path is documented (Task Scheduler entry name, registry Run key, startup folder file), add it with a citation.

### 4.6 `CREDENTIAL_FILES`

Paths the worm is documented to sweep. The scanner **lists their presence only** — never reads them. See §5.3.

```
~/.npmrc
~/.gitconfig
~/.config/gcloud/application_default_credentials.json
~/.aws/credentials
~/.ssh/id_rsa
~/.ssh/id_ed25519
~/.ssh/id_ecdsa
```

### 4.7 Authoritative external sources for updates

When extending any of the constants above, the canonical sources are (in this order of authority):

1. **Datadog IOC repo** — `https://github.com/DataDog/indicators-of-compromise/tree/main/shai-hulud-2.0` — the most actively maintained machine-readable IOC list for this worm family. Mirror new file hashes / domains / package names from here first.
2. **CISA advisory** — `https://www.cisa.gov/news-events/alerts/2025/09/23/widespread-supply-chain-compromise-impacting-npm-ecosystem`.
3. **Wiz blog** — `https://www.wiz.io/blog/mini-shai-hulud-strikes-again-tanstack-more-npm-packages-compromised`.
4. **Datadog Security Labs writeup** — `https://securitylabs.datadoghq.com/articles/shai-hulud-2.0-npm-worm/`.
5. **StepSecurity post-mortems** — `https://www.stepsecurity.io/blog/ctrl-tinycolor-and-40-npm-packages-compromised`.

**Do not add patterns from unverified user reports, Twitter/X threads alone, or screenshot-only sources.** False-positives in a forensic scanner cause real harm: they prolong incident response, encourage developers to wipe machines that were never infected, and erode trust in subsequent true-positive findings.

## 5. Safety invariants — **do not regress under any circumstances**

These are not style preferences. Each one exists because regressing it causes irreversible damage to a victim's data, credentials, or machine. If a future refactor appears to require breaking one of these, **stop and ask the user** — there is almost always another way.

### 5.1 Never execute target package code

Tarballs are read in memory via `tarfile.open(fileobj=io.BytesIO(data), mode="r:gz")`. Members are inspected via `extractfile()` (which returns a `BufferedReader`, not a path on disk) and `decode("utf-8", errors="replace")`. **At no point is the tarball extracted to a temporary directory, nor any file inside it `import`-ed, `exec`-ed, `eval`-ed, or passed to `node` / `bun` / `python -c`.**

The whole point of `--check` is to inspect a package *before* installing — running it would defeat that purpose and would risk auto-detonating the very payload the user is trying to identify.

Preserve this if refactoring `scan_tarball_bytes`. Do not add a "convenient" `tarfile.extractall()` even with `members=` filtering — a malicious tarball with path-traversal members can escape even a restricted extract. In-memory `extractfile` cannot escape because nothing is written to disk.

### 5.2 Never auto-revoke tokens, never auto-rotate credentials

The worm's `gh-token-monitor` daemon polls GitHub every 60 seconds. **If it detects a token revocation, it triggers `rm -rf ~/` (Linux/macOS) or the Windows equivalent.** Revocation is therefore the most dangerous action on an infected machine, and it must happen *after* the daemon has been removed.

The scanner:
- Warns loudly when the daemon path is present (Check 1/6).
- Provides an auto-fix that stops + disables + deletes the daemon file, with per-finding confirm prompts in v2.0.
- **Defers all credential rotation to a printed manual checklist** — Step 5 of the incident guide, and the "MANUAL STEPS REQUIRED" section of the auto-fixer.

**Never call `gh auth logout`, `npm token revoke`, `aws iam delete-access-key`, `gcloud auth revoke`, `az ad sp credential reset`, or any equivalent from the scanner.** Even if a future "convenience" feature seems valuable, do not add it without explicit, signed-off discussion in CLAUDE.md updates and the README.

### 5.3 Never read credential file contents

Check 5 in `run_scan` lists credential file paths only. It calls `Path.exists()` and emits a Finding whose `detail` contains paths and severity guidance. **It never calls `Path.read_text()` / `read_bytes()` on these files**, never logs their contents to the report, never sends them anywhere.

The diagnosis report also lists credential file presence as `[EXISTS]` / `[absent]` only — basenames and paths, never values.

This rule extends to any future feature: memory snapshots, "include context for LLM", auto-upload, telemetry, etc. If a feature appears to need credential contents, redesign the feature.

### 5.4 Never make the scanner phone home

The scanner makes outbound HTTPS calls **only** to:
- `https://registry.npmjs.org/<package>` — JSON metadata fetch (`--check` mode only)
- The `dist.tarball` URL returned by the above metadata (npm CDN) — tarball fetch (`--check` mode only)

No telemetry. No crash reporting. No analytics. No `requests.get(<anything-else>)`. The diagnosis report is **written to a local file** and the user pastes it themselves into an LLM — the scanner does not transmit it.

### 5.5 Pattern additions require a public source

Every new entry in `MALICIOUS_PATTERNS` or `KNOWN_BAD` must be backed by one of the sources listed in §4.7. Add the source URL in a comment on the line above the entry. This is the project's contributing rule (in README.md "Contributing" section) and it exists because a regex shipped in this tool can mark someone's machine as infected — which they may then wipe.

### 5.6 The Unicode escape pattern is deliberately ASCII-scoped

`MALICIOUS_PATTERNS` contains:

```python
(r"(?:\\u00[2-7][0-9a-fA-F]){4,}",
 "ASCII chars encoded as \\u escapes (obfuscation)",  "MEDIUM"),
```

This is scoped to ` `–`` (printable ASCII) on purpose. **Do not broaden it to `\u01xx`–`\uFFxx`.** Real i18n libraries (`lodash`, `core-js`, `linebreak`, Intl polyfills) legitimately encode Unicode character tables with high-codepoint `\uXXXX` sequences. Broadening this regex floods scans of any sufficiently large `node_modules` with false-positives, and the user starts ignoring real findings.

If you ever do touch this regex, regression-test against a real lodash 4.x bundle and at least one i18n polyfill before merging.

### 5.7 The 8-step incident guide ordering is load-bearing

The order of the steps in `show_incident_guide()` / `run_incident()` (STOP → ISOLATE → IMAGE → REMOVE DAEMON → ROTATE CREDS → AUDIT PUBLISH → REBUILD → REPORT) reflects real operational constraints. In particular:

- **STOP comes before everything** because revoking tokens before the daemon is removed triggers home-directory wipe (see §5.2).
- **ISOLATE comes before IMAGE** because the worm continues to exfiltrate while the disk is being imaged otherwise.
- **IMAGE comes before REMOVE DAEMON** because forensic evidence is destroyed once the daemon and its filesystem artifacts are deleted.

Do not "tidy up" this ordering for readability. Do not collapse steps. Do not add an early "revoke tokens" step.

### 5.8 Cross-machine portability — what to be careful about

This tool runs on Linux, macOS, and Windows, on developer laptops and CI runners, on bare metal and in containers. Specific portability rules:

- **No hardcoded shell.** Use `subprocess.run([list, of, args])` — never `subprocess.run("cmd ...", shell=True)`. shell=True changes the quoting model per OS and is a command-injection surface for any value that flows in from the registry or filesystem.
- **No POSIX-only path operations.** Use `pathlib.Path` and `Path.home()`, not `os.path.expanduser` strings glued by hand, and never assume `/`.
- **Per-OS branches use `platform.system().lower()`** — values are `"linux" | "darwin" | "windows"`. Stay consistent with the existing branches in `DAEMON_PATHS` and `run_scan`'s daemon check.
- **ANSI colour on Windows** is enabled via `_enable_ansi_windows()` (v2.0) which uses `ctypes.windll.kernel32.SetConsoleMode(handle, 7)`. v1.1 uses an env-var heuristic. If you add new colour output, route it through `_c()` — never embed escape sequences directly.
- **`subprocess` calls have explicit `timeout=`.** A hanging `npm config get` should not freeze a scanner that a user is running because they suspect active infection.
- **Encoding is `utf-8` with `errors="replace"`** for every file read. A binary file in `node_modules` (rare but possible) must not crash the scan.

### 5.9 Impact awareness

This tool is run in two very different states, and the cost of being wrong in each is asymmetric:

| State | Cost of false negative | Cost of false positive |
|---|---|---|
| **Pre-install (`--check`)** | Developer installs malicious package → full machine + org compromise | Developer doesn't install a clean package → minor inconvenience |
| **Post-suspected-infection (`--scan`)** | Victim believes machine is clean → continues using compromised tokens, exfiltration continues | Victim wipes a clean machine → significant lost work, lost local-only data, eroded trust in scanner |

Be conservative on `--check` (prefer false-positives there: a missed install of a poisoned package is catastrophic). Be precise on `--scan` (prefer false-negatives there to false-positives: incorrectly telling someone they're infected has real cost — see CISA reports on incident-response fatigue).

2. Run `--check` against a known-clean package (e.g. `python shai_hulud_guard.py --check lodash@4.17.21`) and a known-compromised one (`@tanstack/react-router@1.169.5`) — both should produce expected output.
3. Read the output. There is no machine-readable success/failure assertion yet.

## 7. Style / project conventions

- **Stdlib only.** No `requests`, no `colorama`, no `click`, no `rich`. The script must run on a freshly-installed Python 3.8 with nothing else.
- **Single-file scripts.** Both v1.1 and v2.0 are single files. Do not split into a package without explicit user instruction — the deploy story (curl one file, run it) is part of the threat-response value proposition.
- **No external network calls outside the npm registry** (see §5.4).
- **Comment with sources.** A regex without a citation is a future false-positive waiting to happen.
- **Match existing severity vocabulary**: `CRITICAL`, `HIGH`, `MEDIUM`, `LOW`, `INFO`. These are strings, not enums — do not "improve" them to an enum without rewriting the comparison sites.
- **Both scripts are kept in sync on IOC data**; UI/UX differences are expected and intentional.

### 8.2 Linter / formatter — `ruff` ✅ DONE

Run with:

```bash
python -m ruff check .                 # report

python -m ruff check . && python -m ruff format . --check   # pre-commit gate
```

Selected rule groups: `E F W I B UP S C4 SIM RET`. The `S` (bandit-equivalent security) group is on because this is a security tool — a `subprocess(shell=True)` slipping in is the kind of thing the linter must catch.

### 8.3 Build / packaging — PyInstaller ✅ DONE

Both versions ship as **single .py files** *and* as **prebuilt single-file binaries** via PyInstaller (`--onefile`).

Build commands:

```bash
python build.py            # build both versions to dist/
python build.py --v2       # build only v2.0  -> dist/shai_hulud_guard[.exe]
python build.py --v1       # build only v1.1  -> dist/shai_hulud_guard_legacy[.exe]
python build.py --clean    # rm -rf build/ dist/ *.spec
```

On Windows: `.\build.ps1` is a thin wrapper around `build.py`. On Linux/macOS: `make build`.

Output binary naming convention:
- `shai_hulud_guard[.exe]` ← v2.0 (the recommended interactive one — README points at this name)
- `shai_hulud_guard_legacy[.exe]` ← v1.1 (CI/scripted use)

**Reproducibility caveat** (documented in `build.py` docstring): PyInstaller bundles the exact Python interpreter + stdlib from the build machine. Identical binaries across machines therefore require pinning Python version + PyInstaller version + a clean container. For genuinely-reproducible release artifacts in the future, build inside a pinned container in CI — but the canonical artifact is and remains the source `.py` file; the binary is convenience.

## 9. Quick reference — most common edits

| You want to … | File / location |
|---|---|
| Add a new IOC regex | `MALICIOUS_PATTERNS` near top of *both* scripts. Cite source in comment. |
| Add a known-bad version | `KNOWN_BAD` near top of *both* scripts. |
| Mark a new package as high-scrutiny (no specific bad version yet) | `KNOWN_BAD[name] = {"bad": [], "waves": [...]}` and it will auto-flow into `HIGH_VALUE_TARGETS`. |
| Add a daemon persistence path | `DAEMON_PATHS[<plat>]`. Per-OS — make sure the path is correct on the target OS. |
| Add a new credential file to *check presence of* | `CREDENTIAL_FILES`. Never read it. |
| Add a new auto-fix | v2.0 only. Construct a closure `fix_fn` that returns `(success: bool, msg: str)` and attach via `Finding(..., fixable=True, fix_label="...", fix_fn=...)`. |
| Add a new proactive protection | v2.0 `build_protections()`. Must include `benefit`, `tradeoffs` (list of strings), `apply_fn`, optional `verify_fn`. |
| Update the incident guide | v1.1 `run_incident()` and v2.0 `show_incident_guide()`. Preserve the 8-step ordering — see §5.7. |
| Touch network code | `_fetch_json` / `_fetch_bytes` (v2.0) or `fetch_json` / `fetch_bytes` (v1.1). Must remain stdlib-only and registry-only — see §5.4. |
